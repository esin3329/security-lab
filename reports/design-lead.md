# security-lab MVP 잔여작업 설계서

- 작성일: 2026-10-12 (Asia/Seoul).
- 대상: `C:\project\security-lab` 전체. WSL 확인 경로는 `/mnt/c/project/security-lab`.
- 최초 작성 범위: **`reports/design-lead.md` 신규 작성만**. 후속 배정 개정은 이 설계서와 최종 통합 보고서의 인계 안내에만 반영하며, 기술 파일 수정·컨테이너 실행·빌드·스캔·익스플로잇은 수행하지 않는다.
- 근거: 아래 현황표의 로컬 파일을 읽은 결과. 실행 성공·도구 설치 성공·측정 결과를 입증하는 문서가 아니다.
- 현행 배정: 사용자 요청에 따라 **agy의 잡무 담당은 유지하고, 나머지 Herdr 에이전트는 고정 역할이 아닌 작업 단위로 분담**한다. 각 작업자가 그 작업의 설계·구현·검증·인계를 맡으며, 완료 후 다음 작업을 새로 배정한다.
- 최초 현황과 기존 Orca Task/Dispatch 완료 기록은 당시의 증거로 유지한다. 최신 MVP 진행 상태는 [최종 통합 보고서](final-integration.md)를 따른다.
- 사용자가 병렬 워크트리 배분을 승인했고 agy를 실행했다. A단계 잔여 구현·문서는 작업별로 배정한다. 실제 대상 기동·스캔·pwn 빌드/실행 및 Phase 2는 이번 배정에 포함하지 않는다.

### 구현에서 먼저 확인할 결함

1. `run.ps1`은 URL과 추가 인자를 합친 문자열에 `^-u$`를 적용한다. URL이 앞에 있으므로 추가 인자 `-u`를 이 조건으로 차단하기 어렵다. 추가 인자를 토큰 단위로 검사해야 한다.
2. `$ErrorActionPreference = 'Stop'` 상태에서 `Write-Error` 뒤에 `exit 2~6`이 있다. 문서가 약속하는 종료 코드에 도달하는지 모의 실행으로 확인하고, 필요하면 오류 출력과 종료 처리를 정리한다.
3. 추가 인자를 그대로 넘기면 별도 대상·입력 파일·출력 경로·시간 제한 같은 옵션으로 래퍼의 경계를 바꿀 가능성이 있다. **고정 Strix 버전의 실제 CLI를 확인한 뒤** 허용 옵션만 통과시키며, 확인하지 못한 옵션은 거부한다.
4. 별도 Strix 컨테이너 안의 `127.0.0.1`/`localhost`는 그 컨테이너 자신이다. 컨테이너 실행 대상은 같은 `targets-net`의 `juice-shop:3000`을 사용하고, loopback 별칭을 무조건 같은 대상으로 치환하지 않는다. VM 호스트용 주소와 컨테이너용 주소를 문서에서 구분한다.
5. `targets-net`은 internal network다. Strix의 외부 LLM 서비스 필요 여부는 아직 확인하지 않았다. 통신이 필요하더라도 대상망의 격리 해제·외부 대상 추가로 해결하지 않는다. 이 MVP에서는 외부 스캔을 허용하지 않으며, 동작이 불가능하면 제한을 보고한다.

## 2. 유지할 MVP 경계와 완료 단계

- 웹 대상은 로컬 VM의 Juice Shop 1개, pwn 문제는 로컬 Phoenix Stack Zero 1개로 한정한다.
- **외부서버 스캔·원격 익스플로잇 금지.** 검증용 거부 입력은 Docker/Strix 호출을 가로챈 모의 실행에서만 다룬다. 실제 네트워크 요청으로 거부 여부를 시험하지 않는다.
- **페이로드·쉘코드·완성 익스플로잇 기록 금지.** 원시 도구 출력도 이 내용이 포함될 수 있으므로 저장소·보고서·로그로 그대로 복사하지 않는다. 성공 여부, 시간, 식별자, 한국어 관찰 요약만 남긴다.
- 이미지·도구·pwndbg는 실제 확인한 버전/커밋으로 고정한다. `latest` 태그, 태그 생략에 따른 암묵적 latest, 기본 브랜치 추적, 자동 업데이트를 사용하지 않는다. 현재 미확정 Strix 버전과 pwndbg 커밋은 임의 값으로 채우지 않는다. PowerShell의 `Set-StrictMode -Version Latest`는 이미지 태그와 별개다.
- **8지표·15분·3회반복·정확한 allowlist 규칙 유지.** 지표 추가, 탐지율/FP율 같은 파생 지표, 정규화 도구 확장은 제외한다.
- **Phase 2 착수 금지:** rea, artex-ko, WebGoat, 자작 API, 추가 pwn 문제, ground-truth 내용 확정은 이번 잔여작업에 포함하지 않는다.

완료 판정은 아래 단계별로 기록한다. 상위 단계가 미완료이면 그 사실을 보고서에 남긴다.

| 단계 | 필요한 증거 | 현재 판단 |
|---|---|---|
| A. 구조적 MVP | T2 구현/거부 검증, T3 문서, 고정 버전, 기록 양식, 통합 체크리스트 | 뼈대는 있으나 잔여작업 있음. 이 설계서가 다루는 우선 범위. |
| B. 로컬 실행 검증 | 사용자가 기존 VM 실행 경계 안에서 기동·도구 확인·15분 종료·3회 기록을 검증한 증거 | 미실행. 문서 작성이나 모의 실행으로 대체해 완료라고 하지 않음. |
| C. 8지표 실측 비교 | 같은 조건의 Strix/수동 기록, 사람의 판정, 확정 ground-truth | ground-truth 미확정으로 현재 차단. Phase 2 자료를 이번 작업에서 만들지 않음. |

## 3. 작업분해표 — T2 / 작업별 기술 분담

**기술 구현을 특정 에이전트의 고정 역할로 두지 않는다.** 최초 배정안은 현재 Herdr에서 확인한 `pi`·`codex`·`opencode`에 독립 작업을 나누는 방식이다. 현재 대화의 `omp`는 작업 큐·승인·진행 보고를 관리하며, 이후 작업 배정은 가용 상태와 파일 경계를 기준으로 다시 정한다. 설계·구현·검토를 특정 에이전트에 영구 고정하지 않는다.

배정 전에는 Herdr의 실제 에이전트 종류·pane ID·작업 경로·입력 가능 상태를 다시 확인한다. 아래 pane ID는 조회 시점의 배정 대상이다. 현재 `agy`도 `wB:p6`에서 확인했다. 작업자는 각각 `.worktrees/` 아래의 독립 checkout을 사용하며, 원본 폴더와 다른 작업자의 checkout은 수정하지 않는다. 기준 커밋은 병렬 작업 시작 전의 기존 파일 스냅샷으로 만들며 원격 저장소나 전역 Git 설정은 변경하지 않는다.

**파일별 수정 소유자는 한 명만 둔다.** T2-1과 T2-2는 같은 래퍼를 수정하므로 하나의 작업으로 묶는다. T2-3 작업자는 래퍼를 수정하지 않고 `benchmarks/metrics.schema.json`과 `tools/strix/metrics.py`를 맡는다. 기록 호출 계약은 `python3 tools/strix/metrics.py --record <완결 JSON 파일> --output <JSONL 파일>`이며, 성공은 종료 코드 0, 입력·기존 로그·중복 ID 거부는 2와 미추가로 구별한다. 래퍼 연결은 T2-1/2 작업자만 수행한다. 미완결 관찰은 측정 JSONL로 채우지 않는다. 문서 수정 요청은 agy에 전달한다. 실제 Docker/Strix/pwn 실행은 기존 사용자 VM 경계를 유지하며, 로컬 구현 검증은 dry-run/모의 실행으로 한다.

| 작업 | 최초 배정 후보 | 대상 / 변경 | 완료 기준 | 의존 / 인계 |
|---|---|---|---|---|
| **T2-1 래퍼 입력 경계** | `pi` / `wB:p2` | `tools/strix/run.ps1`, `targets.allow`. 기존 URL·추가 인자 거부 보강을 유지하고 남은 동작 검증을 수행한다. | 허용 3개 host:port 규칙 유지. 부적합 URL/스킴, 목록 외 대상, 범위 입력, 업데이트·추가 대상 옵션은 실행 전에 거부. 문서화된 종료 코드와 거부 시 실제 Docker/Strix 호출 0회를 모의 실행으로 확인. | T2-2와 한 Task. 기존 완료 내용을 다시 구현하지 않으며, 필요한 고정 CLI 확인과 실행 검증을 함께 인계. |

| **T2-5 기술 검증·통합 검토** | 구현 결과 인계 후 가용 에이전트에 별도 Task로 배정 | T2-1~4의 결과와 작업별 검증 자료. 검토 중 구현 파일을 대신 수정하지 않는다. | 입력 거부·허용, 시간 초과·정리, 종료 코드, 버전 및 JSONL 계약의 관찰 결과를 대조. 로컬 검증과 VM 미실행 항목을 구분하고 문서 정합성까지 확인. | T2-1~4 결과와 관련 T3 문서 인계 후 수행. 자신이 작성한 부분만으로 통과 판정을 내리지 않도록 다른 작업자의 검토를 배정. 수정은 해당 파일 소유자에게 반환. |

`infra/compose.targets.yml`에 신규 타겟·공개 바인딩·외부 통신망을 추가하지 않는다. 기존 설정이 충분하면 수정 없이 정적 검토 결과만 제출한다. apt 패키지 등 빌드 결과의 도구 버전은 VM 검증 시 기록하며, 이번 작업을 별도 패키지 미러/공급망 시스템 구축으로 확장하지 않는다.

## 4. 작업분해표 — T3 / agy 잡무·문서 정리

## 5. 최종 통합 계약과 순서

### 측정·실행 계약

1. **같은 조건:** Juice Shop 버전, Strix 버전/설정, allowlist, 초기 상태, VM 자원, 모델 설정을 고정해 기록한다. 상태를 유지하는 named volume이 있으므로 3회 시작 상태가 달라지지 않도록 사용자 VM 검증에서 초기화 기준을 정한다. 결과 간 차이는 숨기지 않는다.
2. **시간·반복:** 대상 작업 상한은 회당 15분(900초), 반복번호는 1·2·3이다. 래퍼 시작~종료 시간은 준비/정리로 900초를 넘을 수 있으므로 실제 초를 기록한다. Strix와 수동 비교를 실제 수행했다면 같은 타겟/조건으로 각각 3회, 총 6회 기록을 확인한다. 이번 문서 작성에서는 수행하지 않는다.
3. **8지표:** `tp`, `fp`, `poc_success_rate`, `duration_sec`, `token_cost`, `human_interventions`, `reproducibility`, `explainability`를 유지한다. TP/FP는 사람이 확정 ground-truth와 대조하며, 재현성은 세 실행을 확인한 뒤 판정한다. pwn 관찰을 이 Strix/수동 비교의 실측값으로 섞지 않는다.
4. **결측치:** ground-truth 미확정, PoC 시도 0회, 토큰/비용 미수집 등을 성공률 0·TP 0·비용 0으로 대체하지 않는다. 표에는 `미측정`/`판정유보`/`시도 없음`과 사유를 적는다. 현재 스키마는 일부 필수 값의 결측치를 표현하지 못하므로, 해당 실행을 완전한 8지표 JSONL로 인증할 수 없다. 결측치 정책의 기술 반영이 필요하면 T2-3 작업자가 코디네이터와 확정하고 agy가 문서화한다. 확정 전에는 단계 C를 차단으로 남기며 스키마에 임의 null·새 enum을 넣지 않는다.
5. **기록:** 완결된 측정은 `benchmarks/metrics.schema.json`에 맞는 한 실행 한 객체로 `logs/` JSONL에 append-only 저장하고, 표·보고서에서 run_id로 연결한다. 미완결 실행은 안전한 상태/관찰 메모로 남겨 완결 측정과 구별한다. 스키마 검증 통과만으로 실제 실행 또는 측정 성공을 주장하지 않는다.
6. **보관:** 원시 stdout/stderr, API 비밀, 공격 상세를 자동 저장하지 않는다. 실패·시간 초과는 종료 코드와 안전한 짧은 관찰로 기록한다. PoC 지표가 있더라도 공격 코드나 구체적인 페이로드를 기록하지 않는다.

### 인계·통합 순서

1. 사용자에게 작업별 대상·완료 기준·배정 후보·의존성·제한을 보고하고 구현 승인을 받는다. 분담 계획 개정만으로 실행하지 않는다. 기존에 완료된 Orca Task/Dispatch를 다시 열거나 보존된 터미널에 무단 입력하지 않는다.
2. 승인 후 실제 Herdr 에이전트 상태와 파일 소유권을 확인해 T2-1/2, T2-3, T2-4를 독립 작업으로 배정한다. agy는 독립적인 범위·진입 안내를 병행할 수 있으나 미정 CLI를 확정된 예시처럼 쓰지 않는다.
3. 각 작업자가 변경 파일·버전 근거·실제 인터페이스·검증 결과·VM 잔여를 전달한다. T2-3 인계 후 T2-1/2 작업자가 기록 호출을 연결하고, agy가 확정 인터페이스로 관련 문서를 마무리한다.
4. 완료된 작업마다 상태와 차단 사유를 갱신하고 다음 작업을 새로 배정한다. T2-5 통합 검토도 별도 작업이며 고정 Codex 역할이 아니다. 검토 작업자는 아래 체크리스트로 결과를 대조하고, 불일치는 해당 파일 소유자에게 반환한다. 코디네이터는 진행·승인·최종 보고를 관리한다.
5. 실제 Docker/Strix/pwn 검증은 기존 방침대로 사용자의 로컬 Ubuntu VM 단계에 남긴다. 측정 자료가 없으면 B/C 미완료를 명시한 상태로 구조적 산출물을 인계한다.

## 6. 최종통합 체크리스트

체크는 증거가 있을 때만 한다. `미실행`/`차단`은 실패 사유와 담당자를 적고, 샘플이나 모의 결과를 실측으로 인정하지 않는다.

## 7. 설계 산출물 검수

- 이 문서는 최초 현황, T2 작업별 기술 분담, T3/agy 잡무, 통합 계약, 최종통합 체크리스트를 포함한다. 후속 개정은 고정 역할을 작업별 배정으로 바꾼 것이며 실제 구현·실행 완료를 뜻하지 않는다.
- 이 작업의 acceptance는 문서 존재와 위 내용 및 3문장 `worker_done` 보고다. T2/T3 구현이나 단계 B/C의 완료를 이 설계 작업의 성과로 보고하지 않는다.
- 파일 읽기와 문서 검수만 수행했다. 외부 자료 다운로드·외부 스캔·원격 익스플로잇·Docker 실행은 수행하지 않았다.
